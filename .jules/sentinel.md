## 2024-05-18 - Fix Local File Inclusion (LFI) in CacheableWebView via AdBlockWebViewClient
**Vulnerability:** The application was vulnerable to LFI because WebViews could load local files via `file://` URIs. While `CacheableWebView` correctly enabled `setAllowFileAccess(true)` to natively load cache/asset files, `shouldInterceptRequest` did not validate if `file://` requests were pointing to allowed directories (like cache or assets), allowing malicious HTML to load sensitive local files (e.g., `/data/data/io.github.sheepdestroyer.materialisheep/shared_prefs/...`). Also, `mLoadedUrls` map was prone to `ConcurrentModificationException` under heavy concurrent background thread loading.
**Learning:** You can't just disable `setAllowFileAccess` because the app *needs* to natively load `.mht` cached files. Also, replacing strings (e.g., `url.replace("file://", "")`) is insecure due to URL encoding bypasses. You must parse the URI and resolve the canonical path to prevent path traversal (`..`). `ConcurrentHashMap` is strictly required in `WebViewClient` since `shouldInterceptRequest` is called by multiple Chromium threads.
**Prevention:** Always validate `file://` access by parsing the URI, safely resolving the canonical path using `java.io.File`, and verifying it falls within expected base directories (e.g., `Context.getCacheDir()`). Return empty responses to block access, and return `null` to natively load allowed files.
